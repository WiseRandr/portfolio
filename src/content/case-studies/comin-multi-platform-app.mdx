## Overview

COMIN is a ride-hailing platform: riders book a trip, and drivers pick them up and take them where they need to go. It is made of four parts that work together in real time: a rider app, a driver app, an API, and a web dashboard for the operations team.

I joined as Lead Frontend Engineer (part-time) and led a team of five engineers across all four parts. Frontend is my specialism; on this project I also designed and built the live-location and queueing changes described below. I was responsible for engineering delivery and reliability as the operational load changed; I didn't own rider or driver acquisition, or marketing.

**Operating context.** During the early production period, the platform had approximately 1,000 rider accounts and 1,000 driver accounts. On a typical day, roughly 50–70 riders were active and around 170 drivers connected over the course of the day, not all at the same time, while they waited for requests. These are approximate figures from memory, not audited analytics or current totals.

## The problem

A ride is a constant exchange between two phones and a server. In early production, that exchange became the bottleneck:

- **Driver locations fell behind.** Positions reached riders late, so cars appeared to jump across the map instead of moving smoothly.
- **Apps froze during rides,** for riders and drivers.
- **Concurrent rides slowed the whole API.** Every active ride kept the API busy, and response times grew as more rides ran at once. AWS database query statistics and Grafana logs showed the slowdown.
- **Route rendering was expensive.** Drawing and redrawing routes in the apps cost performance on the device and money on map requests.
- **Start-up loaded everything at once.** On launch, the apps waited for the user's full profile and history before showing anything.

## Key decisions and trade-offs

### Redis for live driver locations, with the database as fallback

Driver positions change every few seconds and are read constantly by riders waiting for a pickup. Writing and reading them through the main database meant they competed with the rest of the API for database time. I moved live driver locations into Redis, so during normal operation the API writes and reads each driver's latest position in memory. A scheduled job persists those positions from Redis to the database every 15 minutes. If Redis is unavailable, the API writes incoming location updates directly to the database and reads locations from there.

The trade-offs are one more service to operate and a fallback that shifts load rather than removing it. During a Redis outage, the API reads and writes driver locations directly in the database. This preserves location updates but returns that high-frequency workload to the main database.

### Queues for ride requests, driver acceptance and payments

Ride requests and payments arrive in bursts, and handling each one the moment it arrived put pressure on the API at the busiest times. I moved them onto job queues. Ride requests are processed several at a time, and a job that crashes can be restarted. Driver acceptance has its own queue, processed one job at a time, to serialize competing driver-acceptance requests. That lowers acceptance-processing concurrency in exchange for simpler coordination. Serializing the jobs reduces concurrent acceptance handling; on its own, it isn't proof that a ride can never be assigned twice.

### Google Maps Navigation SDK in the driver app

A teammate embedded the Google Maps Navigation SDK in the driver app, and I helped with the integration later. Drivers get turn-by-turn guidance without switching to a separate navigation app mid-ride, and the SDK draws the route and recalculates it when a driver misses a turn or traffic changes, which took route rendering and rerouting out of our own code. COMIN's agreement with Google billed navigation per completed ride. That was specific to COMIN's contract: [Google's standard pricing](https://developers.google.com/maps/documentation/navigation/android-sdk/pricing) bills per requested destination, with no extra charge for route changes after a destination is fetched. The cost is a dependency on a native SDK, with its own pricing terms and upgrade cycle.

### NestJS modules for the API

We built the API with NestJS. Its modules gave each domain, such as rides, payments and users, a clear boundary, which made a heavy API easier to split up, reason about and maintain as a team.

### Frontend architecture and start-up

- **A shared private module.** I created a private package installed by both the rider app and the driver app, so the two stay consistent in design and behaviour without duplicating code.
- **Redux for state management.** One predictable pattern for state across both apps, so anyone on the team could work in any part of the code.
- **A lighter first screen.** The first screen only needs the user's name, email and last-used location, but the apps used to fetch everything on launch, including their rating, recent rides, and news and offers. I changed start-up to load just those details first and the rest afterwards, which made start-up faster.

## Results

- **More completed rides:** within two months, completed rides went from 4–5 to 20–30 a day, on about 50 ride requests a day. The technical changes and the marketing team's outreach to users both contributed, so this is the product's overall result, not a measurement of any single change.
- **Fewer freezes, more timely positions:** following the changes, we observed fewer freezes during rides and more timely driver-location updates on riders' maps. These were qualitative observations; I no longer have the reporting window or retained measurements.
- **Faster start-up:** both apps show the first screen once its own details arrive, instead of waiting for the full profile and history.
- **In-app navigation:** drivers no longer leave the app to navigate.

## What I'd do differently

### Isolate ride workloads with independently deployed services

The NestJS API was organized into modules, but they all ran in the same deployment and shared its runtime resources. AWS database query statistics and Grafana logs showed the API, and the operations dashboard with it, slowing down when ride traffic was high. What they didn't establish was which shared resource was the constraint.

Before extracting anything, I'd profile to separate two possible causes. If profiling confirmed that shared runtime capacity contributed, deploying the ride workload as its own service, with its own resource allocation and scaling, could leave the rest of the platform more headroom during a spike. If the bottleneck was the shared database, a separate deployment wouldn't fix it on its own; that would need its own measures.

Services aren't free: they bring more deployments to operate, tracing and monitoring across service boundaries, and network calls that can fail where modules used to call each other in process.
