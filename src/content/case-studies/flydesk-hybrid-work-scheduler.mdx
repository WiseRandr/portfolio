## Context

FLYDESK is a location scheduler for hybrid teams. Before the week starts, people record where they'll work (remote, in the office, or in a co-working space) and when, and the schedule becomes visible to the people who are allowed to see it.

The product had three parts: a React Native app where employees sign in with their email and see their schedule for a selected company, a React dashboard the internal team used to configure the system, and a NestJS API behind both.

## The constraints

Scheduling sounds simple until every company does it differently:

- **Locations are open-ended.** A person can work from almost anywhere, and every company names and groups its places differently. Free text is too vague to query or act on, so locations needed a real structure.
- **Time-slot rules differ per company.** One company lets a person be remote in the morning and in the office in the afternoon; another doesn't allow split days at all. The rules had to be configurable, not hard-coded.
- **Visibility depends on groups and permissions.** Some schedules are visible only to a certain group, so every read had to respect who is allowed to see what.

## Team decisions and data flow

Two decisions shaped the backend. I helped set them up; the team made them.

<FlydeskDataFlowDiagram />

### A queued import for bulk users

Most users didn't sign up one by one: companies imported their people in bulk, and an import could be large. Each record was placed on a Kafka queue and processed individually, so an import didn't have to be written to PostgreSQL as a single burst.

### A graph representation for relationship-heavy reads

Locations, time-slot rules, groups and permissions linked differently from one type of user to another, and resolving those links through relational joins made per-user queries slow. The team kept PostgreSQL as the primary store and added Neo4j as a secondary graph representation, synchronized through Kafka, which was already part of the design.

## Results

- **Company-specific scheduling policies** in one product, configured rather than hard-coded.
- **Bulk imports processed through a queue,** record by record.
- **Per-user reads.** The team observed faster per-user queries after introducing the graph representation; retained benchmarks are unavailable.

## What I'd do differently

### Test policy and permission combinations from the start

We didn't have the testing we needed, in the code or at the product level. With policies that differ per company and visibility that differs per group, the risk isn't one rule breaking: it's a new configuration quietly breaking an existing combination. Today I'd start with a small matrix of policy and permission scenarios and keep it running as configurations grow.

<FlydeskTestMatrix />

Each layer proves something different. UI tests cover the feedback and interaction, like the conflict message and the allowed alternative. API tests cover enforcement: the API must reject a schedule that breaks the policy and must not return a schedule to someone outside the group, whatever the interface shows. Integration tests run the real components together, because tests against mocks don't establish that the production pieces integrate correctly.

### Validate the data model before adding a second store

Keeping PostgreSQL and Neo4j consistent caused bugs and delays for the backend team. The decision was made under constraints this write-up may not capture, so I'm not calling it wrong. But today I'd work through the evidence first:

1. Inspect the slow query patterns and their query plans.
2. Review the schema and indexes against those patterns.
3. Measure representative workloads.
4. Consider query or read-model changes within the primary store.
5. Add a second store only when that evidence justifies the cost.

A second store also brings a consistency trade-off: updates may not appear immediately in the secondary store, so synchronization has to be monitored and, when it fails, recovered.
