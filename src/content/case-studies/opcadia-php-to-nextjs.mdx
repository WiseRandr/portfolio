## Context

Opcadia sells personalised study plans online. Its storefront was a basic PHP website: customers couldn't configure a course themselves, and had to send their preferences in and wait for them to be validated before they could see what their plan would look like.

I was a contract frontend engineer, and I led the rebuild of the platform as a Next.js e-commerce application, delivered within six months.

## The problem

The constraints came from how the legacy site had been built, not from PHP itself:

- **A manual buying journey.** Customers had to send their preferences and wait for validation before they could preview a course plan. Every purchase depended on a back-and-forth.
- **An interface without interactive choices.** The existing pages were slow, and they had no way for customers to configure a course themselves.
- **No component reuse.** Each change meant duplicating markup, which slowed the team down and made the site inconsistent.

## My role

I led the project from planning through to production:

- **Scoping:** audited the existing platform, mapped the parts of the customer journey that needed to change, and turned them into a delivery plan.
- **Technical direction:** chose the framework and the architecture.
- **UX foundations:** designed the core user flows and the base UI for course selection and preview, including CSS animations.
- **Team leadership:** split the work across the team and reviewed code.
- **Delivery:** deployed the application and maintained it after launch.
- **Page checks:** used Lighthouse and PageSpeed Insights to review page performance and automated SEO checks.

## Key decisions

### Why Next.js

Next.js covered the rebuild's main needs in one framework:

- **API routes** to serve cached course data, so the frontend could build previews without a manual step.
- **A React component model** for a reusable, consistent UI across pages.
- **Static rendering** for the public pages, so they're served as ready-made HTML.
- **A simple deployment** on Vercel, easier to run than the legacy stack.

### Instant course previews without waiting for validation

The biggest change for customers was removing the wait. Customers configured their course directly on the site and saw their plan immediately. We built the preview on the frontend from cached course data served by Next.js API routes, so details appeared as soon as a customer made a choice.

This turned a manual request into a self-service flow, with a dashboard where customers could review their plan and follow the live status of their enrolment.

### Migrating with a big-bang switch

We replaced the PHP site in a single cut-over rather than page by page. While the new site was in development, its `robots.txt` blocked search engine crawlers until launch. At cut-over we shut down the PHP server and pointed the production domain at the Next.js application on Vercel.

## Results

- **Self-service course configuration:** customers choose their own options, with no manual request.
- **Instant plan previews** instead of waiting for validation.
- **Live enrolment status** visible on the website.
- **Reusable components** in place of duplicated markup.
- **Delivered within six months.**

## What I'd do differently

### Design the data model before the API

I focused first on the UI and UX, and didn't set a clear plan for how the cached data behind the API should be structured. We ended up with several overlapping API routes, which made the pages harder to manage early on. We fixed it by regrouping the data in MongoDB, but a data-model plan up front would have avoided that rework.

### Add tests from the start

We left unit tests out at first because the early work was mostly UI and didn't change business logic. About three months in, several components were changing continuously as new features landed, and we added unit tests to catch regressions. Today I'd add tests from day one for any component that's likely to keep evolving.

### Plan the cut-over for search, not only for launch

Our safeguard was limited to `robots.txt`. Blocking crawling isn't the same as preventing indexing: a blocked URL can still appear in search results if other pages link to it. Today I'd protect the pre-launch site with authentication, or with a `noindex` directive that crawlers are allowed to read, map old URLs to new ones with redirects, check canonical URLs before launch, and keep a rollback plan for the cut-over.
